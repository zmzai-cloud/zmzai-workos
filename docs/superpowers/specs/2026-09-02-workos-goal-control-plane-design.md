# workos 工作台第二阶段设计：目标与工作的控制面

日期：2026-09-02 · 仓库：`zmzai-workos`（`i.zmzai.cloud`）

## 决策摘要

workos 不再只是产品导航或 Agent 摘要页，而是面向 AI 创作者的统一工作入口：用户从一个自然语言目标开始，创建并跟进 Agent 工作，处理需要人工介入的事项，并在同一处获得、归档或继续加工产物。

第一版优先服务 AI 创作者／开发者；普通 Agent 用户和产品矩阵客户是后续兼容的人群。核心体验为「A + B」：一眼看到所有待推进工作，也能直接创建新目标。工作台内可创建 Agent 任务，但实际执行仍由 `zmzai-agent` 承担。

## 用户与待完成任务

目标用户每天进入工作台时，需要完成：

1. 知道哪些目标正推进、哪些等待自己处理、哪些被阻塞；
2. 用一句话发起一个新的工作目标；
3. 在不中断上下文的情况下取得或继续使用结果。

成功不是展示更多模块，而是让用户完成闭环：

`目标 → Agent 计划与执行 → 用户确认／处理阻塞 → 产物收件箱 → 项目知识或下一目标`

## 首版信息架构

### 今日工作（默认首页）

1. **目标输入**：自然语言描述目标；可选项目与背景资料；提交后创建对应 Agent 任务。
2. **推进队列**：分为进行中、等我处理、已阻塞和已完成。卡片展示标题、阶段、最后更新时间与首要操作。
3. **结果收件箱**：展示已完成任务的报告、网页、代码、文件等产物；用户可以查看、下载、归档为项目知识，或以产物为上下文继续创建目标。
4. **需要关注**：集中提示失败、授权／选择、预算预警、逾期风险。待人工介入不能被伪装成完成或空态。

### 上下文导航

- **项目**：目标的稳定归属，聚合目标、资料与产物。
- **知识**：项目资料、提示词和可复用结论；首版以关联、计数和归档为主，不做复杂编辑器。
- **用量**：Relay 用量与预算摘要。
- **产品入口**：Agent、Relay、教程和主站保留为辅助入口，不占首屏主任务。

## MVP 范围

### 交付

- 目标、项目、Agent 任务之间的关联模型；
- 在 workos 内创建 Agent 任务；
- 统一状态队列和状态映射：运行中、待处理、阻塞、完成、失败；
- 结果收件箱，以及将结果归档到项目知识；
- Relay 用量摘要与预算阈值提醒；
- 不可达、失败和空数据三种状态的明确区分；
- 上述动作的基础埋点。

### 不交付

- 可视化跨 Agent 编排器；
- 自动发布到第三方渠道；
- 多人协作、审批流；
- 重复 Relay 的模型网关／账单能力；
- 复杂知识编辑器。

## 系统边界与数据流

workos 是目标、项目、关联关系和聚合视图的权威来源；Agent 是执行任务、检查点、状态细节与产物的权威来源；Relay 是模型用量与计费的权威来源。

1. 用户在 workos 创建目标，选择或新建项目，并附带可访问的资料引用。
2. workos 调用 Agent 的内部命令 API，创建执行任务并保存 `goalId ↔ agentTaskId` 映射。
3. workos 通过受服务鉴权保护的摘要／详情 API 拉取任务状态、检查点和产物；首版可采用短轮询，后续再升级事件推送。
4. workos 聚合状态，生成推进队列与需要关注项；Relay 的只读摘要独立接入，不能阻断任务状态读取。
5. 用户对待处理项作出确认、重试或继续操作时，workos 将命令转发给 Agent，并记录操作与时间。
6. 已完成产物以引用方式进入收件箱；归档操作只建立项目知识关联，避免不必要复制。

内部 API 必须使用服务间 Bearer 密钥、轮换支持、最小化返回字段和 `no-store`；workos 不直查 Agent 的业务集合，也不向 Agent 透传用户 cookie。

## 状态与异常策略

| 情况 | UI 行为 | 数据处理 |
| --- | --- | --- |
| Agent 暂不可达 | 显示上次成功同步的快照及“状态可能已过期”；提供重试 | 保留快照与同步时间，不以空列表覆盖 |
| Relay 暂不可达 | 仅用量区域显示不可用 | 任务队列继续可用 |
| Agent 任务失败 | 展示失败阶段、可读原因与重试入口 | 保留原目标与上下文 |
| 需要人工确认／授权 | 进入“等我处理” | 记录待处理原因和可执行动作 |
| 预算阈值触发 | 显示提醒 | 首版不自动停止任务 |
| 无目标／无任务 | 显示引导创建首个目标 | 与服务错误严格区分 |

## 衡量成功

上线后 30 天内观测：

- 目标创建率：登录用户中创建过目标的比例，目标 ≥ 30%；
- 任务续办率：运行中任务至少被用户回访、确认或继续一次的比例；
- 结果闭环率：已完成任务的产物被打开、下载、归档或用于下一目标的比例，目标 ≥ 50%；
- 7 日回流率：创建过目标的用户在七日内再次进入工作台的比例。

事件至少覆盖 `goal_created`、`task_opened`、`task_actioned`、`task_failed`、`artifact_opened`、`artifact_archived`、`goal_continued` 和 `budget_alert_seen`。

## 实施顺序与验收

1. 建立目标／项目模型，以及 workos 创建 Agent 任务的内部命令契约。
2. 建立统一任务队列和状态映射，支持待确认、阻塞、失败与重试。
3. 接入产物收件箱与项目知识归档。
4. 接入 Relay 用量摘要、预算提醒和通知。
5. 补齐埋点、空态、降级态与端到端测试。

一个端到端验收场景必须成功：用户创建目标 → Agent 任务被创建 → 用户在工作台看到状态变化 → 用户完成一次待处理动作 → 用户在收件箱打开产物并归档或基于它继续创建目标。

测试覆盖：身份与项目访问控制、服务间鉴权、状态映射、Agent／Relay 超时降级、重复提交幂等、任务重试、产物访问授权以及该主链路的浏览器端到端测试。

## 迁移原则

既有 `/dashboard` 的最近任务、知识库概览和产品快捷入口保留为兼容内容，但逐步重组到「今日工作」和上下文导航。迁移期间，不改变 Agent 或 Relay 的权威数据归属；新增的 workos 数据只记录关联、用户意图和聚合状态。
